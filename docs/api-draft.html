COKOYO API 案
大学側に実装をお願いしたいエンドポイント（たたき台）

MACアドレスはリクエストにもレスポンスにも一切出てきません。アプリが扱うのは 本人トークンと通行証の2種類だけです。パスとフィールド名は例なので、既存の命名規則に合わせて変更可能です。

01認証は2系統

同じAPIでも、本人トークンで来た呼び出しは設定を変えられ、通行証で来た呼び出しは在否を1件読めるだけ。

本人トークン

自分の設定を変える鍵。keio.jp のログイン、または本人登録で発行。

Authorization: Bearer <user_token>

通行証

相手に渡す鍵。読み取り専用で、1枚ごとに範囲と有効・無効を持つ。

Authorization: Pass <pass_token>

02エンドポイント

ベースURLは仮に /presence/v1。全部で8本、うち通行証で叩くのは GET /presence の1本だけ。

POST /presence/v1/me/register 本人トークン
本人登録。学内Wi‑Fiに繋いだ状態で呼ぶと、その接続元の端末を本人のものとして登録する。
REQUEST
{
  "device_label": "iPhone"   // 任意
}
RESPONSE 200
{
  "device_id": "dev_3a91",
  "registered_at": "2026-09-15T00:10:00+09:00"
}
MACはリクエストに含めません。サーバー側が接続元セッション（DHCP / RADIUS）から引く前提です。 ユーザーに入力させると他人のMACを登録できてしまうため。
POST /presence/v1/passes 本人トークン
通行証を1枚発行する。相手ごとに1枚つくり、アプリが相手に渡す。
REQUEST
{
  "scope": "campus",      // campus | building
  "label": "たろう"        // 自分用のメモ
}
RESPONSE 201
{
  "pass_id": "pass_7f3a",
  "token": "p_9Xk2…",      // 相手に渡す値
  "scope": "campus",
  "status": "active"
}
GET /presence/v1/passes 本人トークン
自分が発行した通行証の一覧。アプリの「誰に見せているか」画面に使う。
RESPONSE 200
{
  "passes": [
    { "pass_id": "pass_7f3a", "label": "たろう", "scope": "campus",   "status": "active",  "last_used_at": "2026-09-14T18:20:00+09:00" },
    { "pass_id": "pass_91c2", "label": "はなこ", "scope": "building", "status": "active",  "last_used_at": "2026-09-14T12:05:00+09:00" }
  ]
}
PATCH /presence/v1/passes/{pass_id} DELETE /presence/v1/passes/{pass_id} 本人トークン
見せる範囲の変更（PATCH）と、1枚だけの無効化（DELETE）。フレンド1人だけの解除はこれで完結する。
PATCH REQUEST
{
  "scope": "building"   // ベストフレンドに昇格
}
DELETE RESPONSE
204 No Content
// 以降このtokenは無効。
// 他の通行証には影響しない。
GET /presence/v1/presence 通行証
在校の問い合わせ。フレンドのアプリが開かれたときに呼ぶ。返るのはその通行証に許された範囲だけ。
RESPONSE — scope: campus
{
  "present": true,
  "as_of": "2026-09-15T00:12:30+09:00"
}
RESPONSE — scope: building
{
  "present": true,
  "building": "南館",
  "as_of": "2026-09-15T00:12:30+09:00"
}
かくれんぼ中も、いないときと同じ形で返す。 {"present": false} のみ。hidden: true のようなフィールドを足すと、 隠していること自体が相手に伝わってしまう。
PUT /presence/v1/me/visibility 本人トークン
かくれんぼのオン / オフ。オンの間は、有効な通行証で来た問い合わせにもすべて「いない」を返す。
REQUEST
{
  "hidden": true,
  "until": "2026-09-15T18:00:00+09:00"  // 任意・自動解除
}
RESPONSE 200
{
  "hidden": true,
  "until": "2026-09-15T18:00:00+09:00"
}
GET /presence/v1/me/presence 本人トークン
自分自身の在校確認。ポイント獲得ボタンを押したときに、本人がキャンパスにいるかを確かめるために使う。
RESPONSE 200
{ "present": true, "building": "南館", "as_of": "2026-09-15T00:12:30+09:00" }

03ステータスコード

200 / 201正常。201は通行証の発行時。
204通行証の無効化に成功。
401本人トークンが無効。再ログインが必要。
403本人登録が学内ネットワーク以外から呼ばれた。
404通行証が存在しない（または無効化済み）。※下の検討ポイント参照
429問い合わせが多すぎる。アプリ側はキャッシュして再試行。

04大学側と決めたい点

1. 本人特定はMACかアカウントか

keiomobile2 は個人アカウントの 802.1X 認証なので、MAC登録を省いて「ログイン中のアカウントの在校」を直接引ける可能性がある。引けるなら /me/register は不要になる。

2. 無効な通行証への返し方

404 を返すと「解除された」と相手に伝わる。角が立たないよう {"present": false} を返し続ける選択肢もある。どちらが良いかは運用方針しだい。

3. 鮮度とキャッシュ

as_of の粒度（リアルタイムか5分前か）と、1通行証あたりの問い合わせ上限。アプリ側はキャッシュ前提で作る。

05まず1本だけなら

試作を進めるための最小エンドポイント

上の8本が難しければ、これ1本があれば残りはアプリ側の模擬で先に作れます。

GET /presence/v1/devices/{mac}
{ "present": true, "as_of": "2026-09-15T00:12:30+09:00" }
ただしこの形はMACを直接扱うため、開発中の限定利用にとどめる想定です。本番では通行証方式に置き換えます。
