COKOYO v1
CNS 限定 / MAC方式 / 通行証なし

対象を SFC の cns 1本に絞り、通行証の台帳を大学側に持ってもらうのをやめた版。 大学への依頼は エンドポイント4本・保存データはアカウント1行 まで縮む。 引き換えに「相手ごとの粒度」と「1人だけ解除」を捨てる。

01前提と、意識的に捨てるもの

APIがMACでしか引けず、COKOYOのサーバーを置かず、フレンドの端末が直接問い合わせる。 この3つが揃うとフレンドは相手のMACそのものを持つしかない。以下はその帰結。

捨てる — 相手ごとの粒度

鍵が1人1本なのでAPIが相手を区別できない。代わりに本人が全員に対する粒度を1つ選ぶ（後述の granularity）。ベストフレンドだけ建物、は作れない。

捨てる — 1人だけ解除

失効はMACのローテーションのみ。全員分が同時に切れるので、残す相手には再配布する。アプリ内ブロックは作らない（表示が消えるだけで相手のアクセスは止まらず、守られていると誤解させるため）。

残る — かくれんぼ

本人単位のフラグなので通行証と無関係に成立する。アプリを経由しない直接アクセスにも効く。いないときと同じ形で返すのも変わらない。

02エンドポイント

ベースURLは仮に /presence/v1。すべてCNSアカウントの本人トークンで認証する。 無記名で叩けるAPIにはしない — 呼び出し元が特定できることで、レート制限も監査も成立し、 「学内の認証済みユーザーだけが使える」と説明できる。

本人トークン（1種類だけ）

CNSアカウントのログインで発行。自分の設定変更にも、フレンドの在否問い合わせにも、同じものを使う。

Authorization: Bearer <user_token>

MAC = フレンドに渡す値

認証には使わない。あくまで「誰について聞いているか」を示すパラメータ。持っているだけでは叩けない。

a2b41c9e7703（小文字16進12桁・区切りなし）
GET /presence/v1/me/mac 本人トークン

自分のMACを取得する。cns に接続した状態で呼ぶ。友達交換に配る値であり、ローテーション検知の起点でもある。

RESPONSE 200
{
  "mac": "a2b41c9e7703",
  "network": "cns",
  "as_of": "2026-09-15T00:10:00+09:00"
}
RESPONSE 409 — cns 以外から
{
  "error": "not_on_cns"
}
これが無いと成立しない。 iOS も Android も、アプリに自端末のMACを渡さない（どちらも 02:00:00:00:00:00 を返す）。 サーバーが送信元IPから DHCP / RADIUS を辿って返す形にすることで、ユーザーに12桁を手入力させずに済む。
POST /presence/v1/presence 本人トークン

在校の問い合わせ。フレンド一覧を開いたときに、全員分をまとめて1往復で聞く。返る粒度は相手が設定した granularity に従う。

REQUEST
{
  "macs": [
    "a2b41c9e7703",
    "6e0d33b1c840"
  ]
}
RESPONSE 200
{
  "results": [
    { "mac": "a2b41c9e7703", "present": true,
      "building": "ι館" },
    { "mac": "6e0d33b1c840", "present": false }
  ],
  "as_of": "2026-09-15T00:10:00+09:00"
}
false は1種類だけにする。 「いない」「かくれんぼ中」「未登録のMAC」「存在しないMAC」を、 レスポンスでも応答時間でも区別できないようにする。区別がつくと、 かくれんぼ中であることや、そのMACが実在することが相手に伝わってしまう。
as_of は5分に丸める。 秒精度で building が返ると、連続して呼ぶだけで移動の軌跡が再構成できる。 「今どこにいるか」と「どう動いたか」は別物なので、後者は渡さない。アプリ側もこの粒度でキャッシュする。
PUT /presence/v1/me/settings 本人トークン

かくれんぼと、全員に対する公開粒度。通行証が無いので相手ごとの出し分けはできないが、本人が1つ選ぶことはできる。

REQUEST
{
  "hidden": false,
  "hidden_until": null,   // 任意・自動解除
  "granularity": "campus"  // campus | building
}
保存されるデータはこれだけ
アカウント1件につき1行:

  account_id   (既にある)
  hidden       bool
  hidden_until timestamp / null
  granularity  enum
既定値は campus。 building は本人が明示的に選んだときだけ。 粒度をクライアント側で絞る案は採らない — APIが建物を返す限り、 アプリを通さず直接叩けば見えてしまうので、境界として機能しない。
GET /presence/v1/me/settings 本人トークン

現在の設定の取得。アプリ再インストール時に状態を復元するために要る。

03友達交換

MAC方式が一番強いのがここ。渡す値が全員に対して同じなので、 QRを1枚出して周りがスキャンするだけで終わる。人数が増えても手順が増えない。 （通行証方式だと相手ごとに別の値を正しい相手にだけ届ける必要があり、端末間のペアリング処理が要る。）

QRのペイロード

アプリ以外が読んでも意味を持たないよう、独自スキームにする。URLにしない（プレビューやスキャン履歴に残るため）。

FORMAT
cokoyo1:a2b41c9e7703:りょうま
10人で一気に交換する場合: 各自が順にQRを出し、残り全員がスキャンする。 10巡で全員が全員を登録できる。ホスト役の端末を立ててローカルで配る方式にもできるが、 v1では実装量を抑えて素のQRで始める。

04壊れ方と、その扱い

この方式は静かに壊れるのが最大の弱点。どちらも「いない」と同じ見え方になるので、 アプリ側で能動的に検知しないと、本人もフレンドも気づかないまま機能が死ぬ。

A. MACのローテーション

iOSの「プライバシー警告をリセット」やネットワーク設定の削除・再接続で、cns 用のランダムMACは変わる。変わった瞬間から全フレンドに present: false が返り続ける。

B. SSIDの取りこぼし

SFCにいても cns ではなく keiomobile2 / eduroam に繋いでいると在校が見えない。端末は前回のSSIDに自動接続するので、本人の意識と無関係に起きる。

C. 相手側の値が古い

相手がAを起こして再配布していない場合、こちらからは永久に「いない」に見える。かくれんぼとも区別がつかない。

対策 — A: アプリ起動時（cns接続中）に GET /me/mac を呼び、保存値と比較する。違っていたら再配布フローへ誘導する。 B: SSIDを読んで（iOS: Access WiFi Information + 位置情報 / Android: ACCESS_FINE_LOCATION）、 学内で cns 以外に繋いでいるときに接続を促す。 C: 交換日と「最後に present: true だった日」を端末内に持ち、長期間falseが続く相手に 「IDが古い可能性」を表示する。完全には解けないので、無言の故障を減らすところまで。

05CNSに確認したいこと

1cns の認証方式と、RADIUS Accounting / DHCP ログの参照可否・保持期間。802.1X なら送信元IP → MAC → アカウント が辿れるので GET /me/mac が成立する。PEAPの内側のidentityがログに残っているかも含めて。
2AP → 館の対応表を持っているか。building 粒度はこれが無いと出せない。
3SFC構内の keiomobile2 / eduroam のAPもCNS管理か。同じログに乗るなら、SSIDを問わず在校を判定できて上のBが消える。ここが一番効く質問。
4レート制限の要件。本人トークン単位で掛ける（学内はIPが共有されるためIP単位は無意味）。バッチ問い合わせ前提なら、1アカウントあたり数分に1回で足りる。
5台帳を持ってもらえる余地。key → アカウント のテーブル1つと発行・失効の2本があれば、相手ごとの粒度と1人だけ解除が戻る。v1をこれに依存させないが、聞くだけ聞いておく。

06v2 に移れる形で作る

クライアントでは MAC と呼ばない

交換する値を friend.mac ではなく friend.presence_key という不透明な文字列としてモデル化する。今そこに入っているのがたまたまMACである、という扱いにする。

後から台帳が手に入ったとき
変えるもの   交換する値（MAC → 発行トークン）
             相手ごとに別値になるためのペアリング処理

変えないもの 交換UI・QR・フレンド一覧・キャッシュ
             POST /presence の呼び出し形
ただし完全には巻き戻せない。 v1で配ったMACは回収できないので、 v2への移行手順には全員のMACローテーション（cns の設定を削除して再接続）を含める必要がある。 v1を選ぶ判断には、この一度きりの片道分が含まれている。
