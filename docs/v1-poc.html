COKOYO v1
PoC / 3層構成 / MAC手入力 / key方式

アプリのサーバーを持たない制約を取り下げ、フロント・バックエンド・DTC API の3層にした版。 MACはバックエンドの中だけに閉じ、ユーザーが扱うのは key だけになる。 引き換えに、MAC ↔ 本人の対応表を自分たちで持つことになった。

00この版で何が変わったか

mac-v1.html は「アプリのサーバーを持たない」を前提に、フレンドがMACそのものを持ち、 大学APIを直接叩く設計だった。この版はバックエンドを1枚挟む。得たものと失ったものは、はっきりしている。

得たもの — 相手ごとの粒度と、1人だけ解除

バックエンドが「key → 誰か」を解決してから connections を見るので、 keyが全員共通の1本でも、scopeとblockは相手ごとに効く。

  • 通行証（1人1本のkey）が要らない
  • QR / LINE で1つの値を配るUXのまま
  • 大学側に台帳を持ってもらう必要がない

失ったもの — サーバーレス原則

README の「アプリ側のサーバーは持たず」は取り下げ。 そしてバックエンドが MAC ↔ 人 の対応表を持つ。元の設計が意図的に避けていたもの。

  • 漏洩時の影響範囲が「参加者全員のMAC」になる
  • 運用者・ホスティング先を決める必要がある

この版の目的

PoC。仕組みが成立することの確認が目的で、悪意ある参加者は想定しない。 本番化のときに必ず塞ぐ穴は 07 と 08 に明記する。

  • フレンドの在校が見えること
  • scope と block が相手ごとに効くこと

013層と、各層が知っていること

設計の中心は MACの壁をバックエンドの内側に引いたこと。 フロントは最後までMACを見ないし、DTC API は最後までkeyを見ない。 ユーザーが自分のMACを入力するのは登録の一度だけで、以降どこにも出てこない。

フロント

ブラウザで動く。端末内に secret とフレンド一覧を持つ。

  • 自分の secret
  • 自分の share_key
  • フレンドの share_key と表示名
  • MACアドレス（登録フォームの一度きり）

バックエンド

唯一 key と MAC の両方を知る層。ここで scope と block を判定する。

  • key ↔ MAC の対応
  • 誰と誰がつながっているか
  • 参加者全員のMAC

DTC API

MACを受け取って在校を返す。COKOYO の存在を知らない。

  • MACと、その在校・位置
  • key
  • 誰と誰がフレンドか
なぜバックエンドを挟むのか。 MACを持っている人は、アプリを経由せず DTC API を直接叩けてしまう。 ユーザーが扱う値をMACではなく key にすることで、「見せる/見せない」の判断をアプリ側で必ず通る場所に置ける。 これがこの層の存在理由で、それゆえ key の扱いを間違えると層ごと意味を失う（→ 02）。

02登録すると2つの値が返る

配る値と、認証する値を分ける。 1つのkeyで兼ねると、LINEでkeyを受け取った相手が「あなたとして」問い合わせられてしまい、 block も scope も守れなくなる。カラム1本で防げるので、PoCでも分ける。

share_key — 配る値

LINEやQRで友達に渡す。公開される前提の値。これ単体では何もできない。

k_7f3a9c21e84b06d5

secret — 配らない値

端末内（localStorage）にだけ置く。「誰が聞いているか」を示す。実質的にアカウント。

Authorization: Bearer s_9b21f04c7ad3e918
どちらもMACから導出しない。 ハッシュ等で導出すると、MACの空間が狭いので総当たりで逆算できる。無関係な128bit乱数にして、対応は persons テーブルの中だけに置く。
共有文字列には表示名を載せる。 keyだけ渡されても誰か分からないので、 受け取った側が端末内に名前を保存する。バックエンドは名前を持たない。 
// LINEに貼る / QRに載せる文字列（URLにはしない）
cokoyo1:k_7f3a9c21e84b06d5:りょうま

03データモデル

key が事実上 person。ログイン画面もアカウント登録もない。 persons の1行が1人で、connections の1行が1つの関係。 

persons
  id             -- 内部ID。外に出さない
  share_key      UNIQUE   -- 配る
  secret         UNIQUE   -- 配らない
  mac            UNIQUE   -- 手入力。小文字16進12桁に正規化して保存
  created_at

connections
  id
  person_low              -- idの小さい方
  person_high             -- idの大きい方
  scope                   -- 'campus' | 'building'  無向・双方に同じ値が効く
  blocked        bool     -- trueで相互に見えなくなる
  created_at
  UNIQUE(person_low, person_high)
(A,B) と (B,A) は id の大小で正規化して1行に畳む。UNIQUE制約で重複を防ぐ。
scope は無向。 どちらかが building にすると、お互いに建物まで見える。相互主義として扱い、どちらからでも変更できる。
MACは保存前に正規化。 手入力なので A2-B4-1C-9E-77-03 も a2:b4:... も来る。 小文字・区切りなし12桁に寄せないと、突合が静かに失敗する。

04エンドポイント

ベースURLは仮に /api/v1。POST /register 以外はすべて secret で認証する。 フロントはこの5本しか叩かない。

POST/api/v1/register 認証なし

自分のMACをフォームから送ると、2つの値が返る。これが唯一MACがフロントを通る瞬間。

REQUEST
{
  "mac": "a2b41c9e7703",
  "name": "りょうま"  // 任意・共有文字列用
}
RESPONSE 200
{
  "share_key": "k_7f3a9c21e84b06d5",
  "secret":    "s_9b21f04c7ad3e918"
}
同じMACの再登録は冪等。 すでに登録済みのMACなら、新規発行せず既存の share_key / secret を返す。毎回新規発行すると、同じ人が複数のpersonに分裂して connections が割れる。
secret を返すのはこの一度だけ。 端末を変えたら再登録（＝同じMACなので同じ値が返る）。
POST/api/v1/connections secret

友達から受け取った share_key でつながる。承認フローなし・即時成立。

REQUEST
{
  "share_key": "k_2c81ff409a7b3d62"
}
RESPONSE 200
{
  "share_key": "k_2c81ff409a7b3d62",
  "scope":     "campus",
  "blocked":   false
}
承認なしの帰結。 keyを持っている人は、相手の同意なく一方的につながれる。 LINEで配る以上そういうものとして扱うが、裏を返すとblockが唯一の対抗手段になるので、 blockはv1に必須。存在しないkeyを指定したときも 200 を返す（→ 06）。
PATCH/api/v1/connections/{share_key} secret

粒度の変更とブロック。無向なので、どちらから変えても両方に効く。

REQUEST
{
  "scope":   "building",  // 任意
  "blocked": true         // 任意
}
RESPONSE 200
{
  "share_key": "k_2c81ff409a7b3d62",
  "scope":     "building",
  "blocked":   true
}
blockは削除と同じ扱い。 行は残すが、以降どちらからも相手が見えなくなる。 解除できる形にしておくと、PoCの検証がしやすい。
POST/api/v1/presence secret

在校の問い合わせ。フレンド一覧を開いたとき、あるいはボタンを押したときに、全員分を1往復で聞く。

REQUEST
{
  "share_keys": [
    "k_2c81ff409a7b3d62",
    "k_55e0a1b7cc94f302"
  ]
}
RESPONSE 200
{
  "results": [
    { "share_key": "k_2c81...", "present": true,
      "building": "ι館" },
    { "share_key": "k_55e0...", "present": false }
  ],
  "as_of": "2026-09-15T12:05:00+09:00"
}
バックエンドの処理順。 ① secret から自分を引く → ② share_key から相手を引く → ③ connections を見て scope と blocked を判定 → ④ 通ったものだけMACに変換して DTC API へ → ⑤ 返ってきた結果を scope に従って削って返す。
scope が campus なら building を落としてから返す。 フロント側で隠す実装にはしない。APIが建物を返す時点で、アプリを通さず見られてしまうため。
GET/api/v1/me secret

自分の share_key とフレンド一覧の取得。再インストール時の復元と、QR表示に使う。

RESPONSE 200
{
  "share_key": "k_7f3a9c21e84b06d5",
  "connections": [
    { "share_key": "k_2c81...", "scope": "building", "blocked": false },
    { "share_key": "k_55e0...", "scope": "campus",   "blocked": true  }
  ]
}
表示名はバックエンドが持たないので、ここには返らない。フロントが端末内の対応表と突き合わせる。 secret を失うと復元できないが、同じMACで再登録すれば同じ値が返るので実質復帰できる。

06見せない情報の設計

false は1種類だけにする。 実装コストはほぼゼロで、後から直すのは面倒な種類のもの。PoCでも最初から入れる。

状況返すもの
本当にキャンパスにいない{ "present": false }
ブロックされている{ "present": false }
つながっていない share_key{ "present": false }
存在しない share_key{ "present": false }
DTC API が落ちている5xx（ここだけは正直に返す）
応答時間も揃える。 ブロックされた相手だけ DTC API を叩かず即座に返ると、 速さの差でブロックされたことが伝わる。打ち切り分もリクエスト全体の完了を待ってから返す。
404 を使わない。 存在しない key に 404 を返すと、そのkeyが実在するかどうかを総当たりで調べられる。 POST /connections も同様に、存在しないkeyでも 200 を返して行だけ作らない。
as_of は5分に丸める。 秒精度で building が返ると、連続して呼ぶだけで移動の軌跡が再構成できる。 「今どこにいるか」と「どう動いたか」は別物なので、後者は渡さない。

07PoCで意図的に捨てるもの

どれも「気づいていない」のではなく「この版では対処しない」と決めたもの。本番化の前に必ず戻ってくる。

登録の検証がない

MACが手入力なので、他人のMACを自分として登録できる。 その人の在校が、登録した人の名前でフレンドに公開される。 UNIQUE制約で二重登録は防げるが、早い者勝ちで先に取られる形は防げない。

MACのローテーションに対応しない

MACが変わると、その人は全フレンドから永久に「いない」に見える。 かくれんぼと区別がつかない。 v1は「変わったら再登録してください」で済ませる。 key は変わらないので、フレンドへの再配布は発生しないのが救い。

承認フローがない

key を持っていれば一方的につながれる。 LINEで配る前提なのでそういうものだが、block が唯一の対抗手段になる。

かくれんぼは保留

本人フラグ1つで実装できるが、v1には入れない。 scope に none を足せば後付けできる形にしておく。 なお意味は変わっていて、MACを知るのがBEだけになった今、 「フレンドに対して隠れる」であって、直接アクセス対策ではない。

ポイントは入れない

在校が見えることの確認が目的。 ポイントは端末内計算で後から足せる。

キャッシュを入れない

フレンド一覧を開くたびに聞きに行く。 人数が少ないPoCでは問題にならない。 レート制限が見えてきたら as_of の粒度に合わせて5分キャッシュを入れる。

08本番化のときの宿題

PoC（DTC APIのモック相手）では問題にならないが、実データに繋ぐ段階で必ず問われる。

  1. DTC API から見た信頼の形が変わっている。 以前の案は「学生本人が自分のトークンで叩く」だったが、この構成では バックエンドが単一のクレデンシャルで、原理的に全学のMACを照会できる。 誰が聞いたかはCNS側から見えず、レート制限もサーバー単位でしか掛けられない。 「なぜ学外サーバーに全件照会権限を渡すのか」への答えを用意しておく。 緩和策としては、本人のCNSトークンを添えて中継し、権限は本人由来のままにする形が考えられる。
  2. MAC ↔ 人 の対応表を自分たちで持つことの扱い。 運用者・ホスティング先・保持期間・漏洩時の影響範囲を決める。 READMEの「アプリ側のサーバーは持たず」の書き換えとセット。
  3. DTC API の契約の確定。 入力は単体かバッチか。建物まで返るか。レート制限と as_of の粒度。 ここが決まるとキャッシュ方針も決まる。
  4. 登録の検証。 最低限「入力されたMACが今キャンパスに在圏しているか」をDTCに確認する。 完全には防げないので、登録・変更の履歴を残すこととセットで。
  5. アカウント方式への乗り換え余地。 DTCが「このアカウントは今いるか」に答えられるなら、MACも登録も検証もローテーションも丸ごと不要になる。 cns は 802.1X なので、Aruba のクライアント情報に username 列が含まれていないかを確認する価値がある。 新規のデータ連携ではなく、既存データに列があるかの確認として聞くのが軽い。
